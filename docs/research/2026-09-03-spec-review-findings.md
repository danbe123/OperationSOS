### 1. [blocker] 15. Milestones
**Issue:** Only milestone 1 has an exit criterion ("ships when a phone can join SOS and see a page"). Milestones 2 to 7 are feature lists with no statement of what must be demonstrably true, no split between what CI can prove on the PC and what must be checked on the Pi, and no numeric targets (search latency, eval hit rate, time to first token, temperature, sizes). A plan cannot mark a milestone done, and section 16's "measure in milestone 6" has nothing to measure against.
**Why:** Without per-milestone acceptance criteria every milestone ends by assertion rather than evidence, the hardware checklist in section 14 is never tied to a milestone, and the plan author has to invent the definition of done for each of seven large work packages.
**Fix:** Append to section 15, after the milestone list:

### Exit criteria

Each milestone closes only when both lists pass. "CI" runs on the PC or in GitHub Actions with no Pi. "Box" runs on the reference hardware and is recorded in `docs/hardware-checklist.md` with date and commit.

2. App shell, library, reader, search. CI: dev stack (section 13) starts with `tests/fixtures/library`; `GET /api/library` lists the fixture ZIM as available; `GET /api/search?q=<fixture term>` returns one Kiwix hit and one FTS5 hit in a single ranked list; a ZIM whose search exceeds 1.5 s is dropped and the response still returns in under 2.5 s; `/api/suggest` returns at most 10; Playwright: Home → search → reader, a link clicked inside the reader iframe stays in the reader, theme persists across reload, all three themes pass an automated contrast check at 1280x720 and 390x844. Box: the same Playwright suite passes against `http://sos.box` from a laptop on the hotspot.
3. Maps. CI: `sos build-maps --fixture` builds `tests/fixtures/maps/` from a 0.1° bbox; `pmtiles verify` passes on every output; Playwright: first tile request returns 206, OSM/OS base switch, overlay toggle, place search from fixture places, pin saved and visible after reload, OSGB grid reference for a known lon/lat equals a precomputed value. ### 2. [blocker] 15. Milestones (plan scope)
**Issue:** The spec asks for a single implementation plan covering a FastAPI backend, a React frontend, a GIS build pipeline, 20 authored scenario playbooks plus 17 modules and 16 cards, a 200GB content sync, an LLM runtime and eval set, and a Pi install script. **Why:** A plan that mixes code, prose authoring and content operations cannot be verified task by task, and the code milestones would be blocked behind content that takes weeks of owner review.
**Fix:** Add to section 15, before the milestone list:

Milestone 4 authoring may start as soon as milestone 2's playbook renderer and validator exist."

### 6. [major] 12. AI assistant (Runtime, Flow, Evaluation) and 14. Testing (AI row)
**Issue:** The prompt has no token budget: three 400-token passages already equal the 1,200 tokens the "60 seconds to first token" figure assumes, before the system prompt, up to four turns of history (capped by turns, not tokens) and the question. With `-c 2048` the prompt plus the generated answer can overflow the context, and the brief measures 1.5 to 5 minutes to first token for 2 to 3k-token contexts. The eval reports "whether the expected source was retrieved" with no pass threshold, requires the model (so it cannot run in CI), and records no timing, so neither the 60-second claim nor the risk-register mitigation "measure in milestone 6" has a number to hit.
**Why:** The fake-llama-server tests would pass while the real box silently truncates passages or takes three minutes per answer, and "run before any model or prompt change lands" has no pass/fail meaning.
**Fix:** In section 12 Flow, after step 5, add: "Token budget, counted with llama-server `/tokenize` before sending: passages at most 1,000 tokens total (three windows of about 330), system prompt at most 150, history at most 400 (oldest turns dropped first), question at most 100, leaving 400 for the answer inside `-c 2048`. sos-api truncates to the budget and refuses to send a prompt over 1,650 tokens."

Replace the Evaluation paragraph with: "`tools/eval/questions.jsonl`: about 50 UK questions with expected source ids. `sos eval --retrieval-only` runs on the PC and in CI with no model and fails if fewer than 90% of questions have the expected source among the three passages. `sos eval` on the Pi additionally generates answers and writes `tools/eval/results/<date>.json` with per-question time to first token, tokens per second, peak RSS and the answer for owner review. In section 14 AI row add: "API test asserts the token budget using the fake server's `/tokenize`."

### 7. [major] 16. Risks and open points (Thermal) and 6. sos-api

### 25. [blocker] 12. AI assistant — Flow for POST /ai/ask, step 1 (and 8. Search — Sources 1 and 2)
**Issue:** The raw question (up to 400 characters) is passed straight to the unified search. libzim's Xapian query parser uses set_default_op(OP_AND) with STEM_ALL and a metadata stopper, and FTS5 MATCH also ANDs terms, so a question like "what should I do if my child has swallowed bleach and is breathing fast" only matches articles containing every non-stopword term. Most ZIMs return nothing, steps 3 to 6 run with zero or one passage, and the model refuses or invents. Separately, raw strings break FTS5 MATCH syntax: '-', apostrophe, ':', '(', '*' and the bare words AND/OR/NOT/NEAR are operators, so "wi-fi", "co-op", "St John's", "1:1 ratio" raise sqlite3.OperationalError: fts5: syntax error.
**Why:** Goal 6 fails for ordinary natural-language questions (retrieval returns nothing) and the search box throws on common UK terms.
**Fix:** Add before step 1: "Query construction. Tokenise the input on non-alphanumerics; lowercase; drop a bundled UK-English stopword and question-word list (what, how, should, do, if, my, can, is, the, ...). For the search box, FTS5 MATCH is built as one double-quoted term per token (`"wi" "fi"`) joined by implicit AND; kiwix gets the tokens space-joined. For /ai/ask, keep at most six content terms; FTS5 uses `"t1" OR "t2" ...` ranked by bm25; kiwix gets the six terms; if fewer than three non-place results come back, retry with the three longest terms. The reduced query is included in the `retrieving` event." Add an API test with inputs `wi-fi`, `St John's`, `999 vs 111`, `1:1 ratio`, `AND`.

### 26. [blocker] 12. AI assistant — Runtime and Flow step 5 (token budget)
**Issue:** The prompt does not fit `-c 2048`. System text (~200 tokens) + three 400-token passages (1,200) + question (400 chars ≈ 100 tokens) + "history capped at four turns" (each turn includes a prior answer whose length is unbounded because n_predict is never set; four exchanges ≈ 1,200 to 1,600 tokens) exceeds 2,048 before any answer tokens. llama-server rejects a prompt longer than the slot context (or, with context shift on, silently drops the start of the prompt, i.e. the system instructions). The "1,200-token context gives roughly 60 seconds to first token" estimate also ignores system, history and question tokens.
**Why:** Every second and later turn in a conversation fails or loses its grounding instructions; first-token latency is understated by 30 to 50 percent.
**Fix:** Replace the budget with: "Token budget (n_ctx 2048): system prompt ≤ 200; passages 3 × ≤ 320 = 960 (trim the lowest-ranked passage first); history ≤ 250 tokens, built from the last two user questions plus the first 60 tokens of each answer, never earlier passages; question ≤ 120 tokens (400 chars); total prompt ≤ 1,530; generation `max_tokens: 400`. Counts use llama-server `POST /tokenize` (fallback: 4 characters per token). The system prompt is placed first and requests send `cache_prompt: true` so its KV prefix is reused. Expected time to first token at 20 tok/s prefill is about 70 s; the UI shows a progress line until the first token."

### 27. [major] 8. Search — Merge and rank
**Issue:** Reciprocal rank fusion assumes the same document appears in several ranked lists. Here every hit belongs to exactly one source list, so Σ 1/(60+rank) has a single term and the score is w / (60 + rank). With k = 60, ranks 1 to 8 give 1/61 = 0.0164 to 1/68 = 0.0147, so any 1.2-weight source at rank 8 (0.0176) outranks any 1.0-weight source at rank 1 (0.0164). The "flat ranked list" is therefore a fixed block order: playbooks/cards, then uk-official/NHS, then medical, then everything else, with the ×1.5 medical boost widening the gap. Within-source rank never crosses a source boundary.
**Why:** A Wikipedia article that is the obvious best answer can never appear above the eighth-best playbook hit; the "one search box across everything" goal degrades to grouped lists.
**Fix:** Replace the two bullets with: "Each hit appears in exactly one source list, so scores are `score = w_source / (k + rank)` with k = 5 (not RRF; there is nothing to fuse). With k = 5 a playbook (w 1.6) hit at rank 4 (0.178) still beats a Wikipedia rank-1 hit (0.167) but rank 5 (0.160) does not; a medical (w 1.2) rank-2 hit (0.171) beats Wikipedia rank 1, rank 3 (0.150) does not." Add these three comparisons as the fixed-input ranking test in section 14. If block ordering is actually intended, say so and drop the RRF wording.

### 28. [major] 8. Search — Sources 3 and Merge and rank (intent boosts)

Prefix matching means "burn" hits Burnley and Burnham, "water" hits Waterloo, "fire", "well", "cross", "church", "mill" all hit thousands of roads and hamlets. So nearly every query returns map junk in the unified list, and the rule "town names that hit fts_places" fires the ×2 place boost on almost any query, pushing map pins above playbooks.
**Why:** Unified search results are polluted and the place boost is effectively always on.
**Fix:** Replace Sources 3 and the place-boost bullet with: "Places enter unified search only when (a) the whole query, or the query with a leading/trailing `near`/`in` removed, exactly equals a place name (FTS5 phrase match with no `*`, then `name = ?` equality check), or (b) the query matches the UK postcode regex `^[A-Z]{1,2}\d[A-Z\d]? ?\d[A-Z]{2}$` (case-insensitive) or a postcode district `^[A-Z]{1,2}\d[A-Z\d]?$`. ### 29. [major] 6. sos-api — Database (`fts_docs`, `fts_places`)
**Issue:** FTS5 indexes every column unless declared UNINDEXED, so `lat`, `lon`, `doc_id`, `kind`, `category`, `scenarios`, `region` and `postcode` all become searchable tokens: a query of `51` or any digit string prefix-matches millions of coordinate tokens, and the index roughly doubles in size. OS Open Names supplies GEOMETRY_X/GEOMETRY_Y in British National Grid (EPSG:27700, 0.1 m resolution), not lat/lon, and the spec has no conversion step and no `pyproj` dependency. No tokenizer is specified (default unicode61 has no stemming, so "burns" misses "burn" in playbooks, while any stemming would corrupt place names), no prefix index for the 2.5M-row place table, no bm25 column weighting, no row-count or size estimate, and OS Open Names' many "Section Of Named Road" rows per road are not collapsed.
**Why:** Wrong or absent coordinates on every GB place, a bloated index that returns nonsense for numeric queries, and slow prefix searches on the largest table in sos.db.
**Fix:** Replace the two FTS5 bullets with:
```
CREATE VIRTUAL TABLE fts_docs USING fts5(
  title, body,
  doc_id UNINDEXED, kind UNINDEXED, category UNINDEXED, scenarios UNINDEXED, page UNINDEXED,
  tokenize='porter unicode61 remove_diacritics 2');
-- ranked with bm25(fts_docs, 5.0, 1.0) so title outweighs body
CREATE VIRTUAL TABLE fts_places USING fts5(
  name,
  kind UNINDEXED, lat UNINDEXED, lon UNINDEXED, region UNINDEXED, postcode UNINDEXED,
  tokenize='unicode61 remove_diacritics 2', prefix='2 3 4');
```
"`sos index` loads OS Open Names CSV rows with LOCAL_TYPE in {City, Town, Village, Hamlet, Other Settlement, Postcode, Named Road}, collapses Section Of Named Road rows to one per (name, POPULATED_PLACE) at their centroid, and converts GEOMETRY_X/Y from EPSG:27700 to EPSG:4326 with `pyproj` (added to api/requirements.txt). NI, RoI, IoM and CI place nodes come from OSM extracts already in WGS84. Expected about 2.5 million rows and 400 to 600 MB in sos.db; the build takes minutes on the Pi and runs only when the source file changes."

### 33. [major] 12. AI assistant — Flow step 6 and `POST /ai/ask` SSE events (section 6)

### 35. [major] 8. Search — Sources 1 (per-ZIM fan-out) and "only ZIMs with a full-text index (checked at rescan time)"

**Why:** Search latency and completeness degrade with library size, and the flagship source silently disappears from results.
**Fix:** Replace Sources 1 with: "Kiwix: ZIMs are grouped by source-weight class (uk-official, NHS, medical, reference, practical, survival, extended), and one multi-book request per class is issued in parallel: `GET /kiwix/search?pattern=<q>&books.name=<a>&books.name=<b>...&format=xml&pageLength=8`. ### 49. [blocker] 5. Services (sos-kiosk.service) and 13. install.sh step 6
**Issue:** The spec runs cage as a system unit AND installs an auto-login drop-in for tty1 as user sos. These are two different, conflicting ways to start a Wayland kiosk: getty autologin gives a shell on tty1 (nothing then starts cage unless a profile script does), while a plain system unit has no logind seat, no VT and no XDG_RUNTIME_DIR, so cage cannot open the DRM device. cage (wlroots 0.18, libseat/logind) needs a real logind session on a VT.
**Why:** As written the kiosk either never appears or fails with a DRM/seat error on first boot, and the implementer cannot tell which mechanism is intended. Milestone 1 ('kiosk showing a placeholder') depends on it.
**Fix:** Delete the auto-login drop-in from step 6 and make the unit itself own tty1:

```

[Unit]
Description=Operation SOS kiosk (cage + Chromium)
Wants=caddy.service
After=caddy.service systemd-user-sessions.service getty@tty1.service
Conflicts=getty@tty1.service

[Service]
User=sos
PAMName=login
TTYPath=/dev/tty1
TTYReset=yes
TTYVHangup=yes
TTYVTDisallocate=yes
StandardInput=tty-fail
StandardOutput=journal
StandardError=journal
UtmpIdentifier=tty1
UtmpMode=user
ExecStart=/usr/bin/cage -- /usr/local/bin/sos-kiosk-app
Restart=always
RestartSec=3

[Install]
WantedBy=graphical.target
```
Install script: `usermod -aG video,input,render sos` and `systemctl set-default graphical.target`. PAMName=login makes pam_systemd create the seat session and XDG_RUNTIME_DIR that cage needs.

### 50. [blocker] 5. Services (sos-storage-event@.service) and 13. sos storage-event
**Issue:** A udev rule matching ENV{ID_FS_LABEL}=="SOS-EXT" cannot deliver the design as written: (a) systemd's udev integration (TAG+="systemd", SYSTEMD_WANTS=) only starts units on add/change, so the 'remove' instance never fires; (b) a RUN+= program runs in udev's private mount namespace with a short kill timeout, so a mount performed there is invisible to the rest of the system or killed; (c) nothing handles the case where kiwix-serve still has a ZIM mmapped when the drive is yanked (reads then SIGBUS and kill kiwix-serve).
**Why:** External-drive hot-plug and removal while browsing is an explicit hardware-checklist item; as specified, unplugging leaves the library marked available and can take kiwix-serve down.
**Fix:** Replace the udev rule and template unit with a mount unit wanted by the label's device unit, plus a service bound to the mount:

```
# /etc/systemd/system/srv-sos-extended.mount
[Unit]
Description=Operation SOS extended library (USB, label SOS-EXT)
BindsTo=dev-disk-by\x2dlabel-SOS\x2dEXT.device
After=dev-disk-by\x2dlabel-SOS\x2dEXT.device
[Mount]
What=/dev/disk/by-label/SOS-EXT
Where=/srv/sos/extended
Type=ext4
Options=noatime
[Install]
WantedBy=dev-disk-by\x2dlabel-SOS\x2dEXT.device

# /etc/systemd/system/sos-extended-rescan.service
[Unit]
BindsTo=srv-sos-extended.mount
After=srv-sos-extended.mount sos-api.service
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/srv/sos/venv/bin/sos storage-event add
ExecStop=/srv/sos/venv/bin/sos storage-event remove
[Install]
WantedBy=srv-sos-extended.mount
```
`sos storage-event add|remove` no longer mounts anything; it only calls `POST /api/system/rescan` (remove regenerates library.xml first so --monitorLibrary drops the books before the umount, and falls back to `umount -l /srv/sos/extended` if the mount is still busy). Add `Restart=on-failure` and `RestartSec=2` to kiwix-serve.service to survive a SIGBUS from a yanked drive. Drop the udev rule from install step 6.

### 52. [major] 8. Search (Sources, item 1)
**Issue:** Querying every full-text ZIM separately in parallel (about 60 core ZIMs) with a 1.5 s timeout per call will not work on this box: kiwix-serve runs a libmicrohttpd pool of `--threads` = 4 (documented default), so 60 simultaneous Xapian queries queue behind four threads on four cores, and a cold Xapian query against the Wikipedia maxi index alone takes seconds from NVMe. ### 57. [minor] 5. Services (backlight) and 6. POST /system/backlight
**Issue:** sos-api is an unprivileged uvicorn process (the spec scopes its only sudo right to the llama unit), but `/sys/class/backlight/*/brightness` is writable by root only.
